CODE-23 — Debugging, Testing, Visualization and Reproducibility

Purpose: Build the engineering discipline required to make AI/ML code trustworthy, debuggable, interpretable and repeatable.

At this point the Coding Book has implemented:

search
ML
neural networks
CNN
RNN/LSTM
Q-learning
policy gradients
NLP
autoencoders
GANs

The algorithms are not the end.

A working AI/ML engineer must also answer:

Did the code do what I intended?
Did the mathematics map correctly to the implementation?
Can I reproduce the result?
Can I detect leakage?
Can I explain unexpected behaviour?
Can I trust the experiment?

This chapter provides the cross-cutting answer.

02

Debugging Layers

👨‍🏫 Teacher Intuition — Bilingual Implementation Model
Machine Learning mein debugging normal software se 10 guna mushkil hoti hai, kyunki model bina kisi syntax error ke crash hue bina chal sakta hai aur bilkul galat results de sakta hai (silent failure)! Agar loss ekdum se `NaN` ho jaye, toh 99% cases mein ya toh learning rate bohot bada hai, ya `log(0)` hua hai, ya `exp(z)` overflow ho gaya hai. Ek accha engineer defensive code likhta hai: har critical function ke aage `assert` lagao, random seed freeze karo, aur unit tests chalao!

When something is wrong, inspect in this order:

Layer 1 — syntax / runtime
Layer 2 — shapes / data types
Layer 3 — data / labels
Layer 4 — mathematical implementation
Layer 5 — optimization
Layer 6 — evaluation protocol
Layer 7 — experiment design

Example:

"Model accuracy is 50%"

Do not immediately change the model.

First ask:

Are the labels correct?
Are the predictions aligned?
Is the loss correct?
Is the split correct?
Is preprocessing leaking information?
03

First Test — Does the Input Look Right?

Before fitting anything:

PYTHON
print(X.shape)
print(X.dtype)
print(X[:5])

print(y.shape)
print(y.dtype)
print(y[:10])

For text:

PYTHON
print(texts[:5])
print(labels[:5])

For images:

PYTHON
print(images.shape)
print(images.dtype)
print(images.min())
print(images.max())

For sequences:

PYTHON
print(
    sequence_batch.shape
)

The most common ML bugs often begin before the model.

04

Assert Invariants

Assertions turn silent errors into immediate failures.

Example:

PYTHON
assert X.ndim == 2
assert len(X) == len(y)

For binary labels:

PYTHON
assert set(
    np.unique(y)
).issubset({0, 1})

For CNN tensors:

PYTHON
assert images.ndim == 4

For PyTorch outputs:

PYTHON
assert logits.shape[0] == labels.shape[0]

Use assertions for properties that must always be true.

05

Shape Discipline

Maintain a shape map in every notebook.

Example:

X        → (n, d)
W1       → (d, h)
b1       → (h,)
Z1       → (n, h)
A1       → (n, h)
W2       → (h, k)
b2       → (k,)
logits   → (n, k)

For CNN:

image
→ (N, C, H, W)

For sequence models:

sequence
→ (N, T, D)

Shape documentation is not cosmetic.

It is executable reasoning.

06

Data-Type Discipline

Check:

PYTHON
print(X.dtype)
print(y.dtype)

Typical issues:

integer data fed where floats are expected
float labels used where class indices are required
object dtype created by mixed Python data

Explicitly convert where appropriate:

PYTHON
X = np.asarray(
    X,
    dtype=np.float32,
)

For PyTorch:

PYTHON
X_tensor = torch.tensor(
    X,
    dtype=torch.float32,
)

Labels for multi-class CrossEntropyLoss are typically integer class indices.

Do not blindly cast every tensor to float.

07

Tiny-Example First Principle

Before using:

60,000 images
1 million rows
large text dataset

test the algorithm on:

3–10 examples

Why?

Because a tiny example allows full manual tracing.

Example:

2 features
2 hidden neurons
1 output

You can calculate:

forward
loss
gradient
update

by hand.

If the tiny case fails, the large case is not worth debugging yet.

08

Manual Trace Table

For iterative algorithms, create a table.

Example for Q-learning:

step state action reward next state old Q target TD error new Q
1 \(s_0\) R 0 \(s_1\) 0 0.9 0.9 0.72

This is far more useful than staring at a Q-table after 5,000 episodes.

09

Numerical Stability Checks

Common danger zones:

log(0)
exp(large number)
division by tiny values
overflow
underflow
NaN
Inf

Check explicitly:

PYTHON
assert np.all(
    np.isfinite(array)
)

For PyTorch:

PYTHON
assert torch.isfinite(
    tensor
).all()

During training:

PYTHON
if not torch.isfinite(loss):
    raise RuntimeError(
        "Non-finite loss detected."
    )
10

NaN Debugging Protocol

When you see:

NaN

immediately inspect:

input
loss
learning rate
gradients
activations
normalization
logs/exponentials

Check:

PYTHON
print(
    torch.isnan(tensor).any()
)

print(
    torch.isinf(tensor).any()
)

The question is:

Where did the first non-finite number appear?

Find that point rather than reacting to the final NaN.

11

Gradient Debugging

For neural networks:

PYTHON
loss.backward()

then:

PYTHON
for name, param in model.named_parameters():
    if param.grad is not None:
        print(
            name,
            param.grad.norm().item(),
        )

Look for:

all zeros
extremely large values
NaN
unexpected missing gradients

Do not assume any one pattern automatically identifies the cause.

12

Gradient Checking

For a small hand-written network, compare analytic gradients with finite differences:

\[ \boxed{ \frac{\partial J}{\partial\theta} \approx \frac{ J(\theta+\epsilon) - J(\theta-\epsilon) } {2\epsilon} } \]

Use a tiny model.

Then compare with:

PYTHON
relative_error(
    analytic,
    numerical,
)

This is especially useful for:

backpropagation
custom layers
custom loss functions
custom RL objectives
13

Test Hierarchy

Use four levels.

Unit test

Tests one function.

Example:

PYTHON
test_sigmoid()

Component test

Tests one model block.

Example:

dense layer
CNN block
RNN cell

Integration test

Tests:

data
→ model
→ loss
→ update

End-to-end test

Tests the whole practical.

Example:

dataset
→ preprocessing
→ training
→ evaluation
→ report

Do not rely only on end-to-end tests.

They are harder to diagnose.

14

Example Unit-Test Pattern

PYTHON
def test_output_shape():
    output = model(
        dummy_input
    )

    assert output.shape == (
        4,
        10,
    )

The exact expected shape should come from the architecture.

Shape tests are cheap and powerful.

15

Property-Based Thinking

Ask what must always be true.

Examples:

Softmax

Each row sums to approximately 1:

PYTHON
assert torch.allclose(
    probs.sum(dim=-1),
    torch.ones(
        probs.shape[0]
    ),
)

Probabilities

PYTHON
assert torch.all(
    probs >= 0
)

assert torch.all(
    probs <= 1
)

Q-table

Q shape = states × actions

Autoencoder

reconstruction shape = input shape

Classification

number of predictions = number of labels

These are invariants.

16

Test Known Mathematical Values

Examples:

PYTHON
assert np.isclose(
    sigmoid(0),
    0.5,
)
PYTHON
assert np.array_equal(
    relu(
        np.array([-2, 0, 3])
    ),
    np.array([0, 0, 3]),
)
PYTHON
assert np.isclose(
    mse_reconstruction_loss(
        np.array([1, 2]),
        np.array([1, 4]),
    ),
    2.0,
)

Known-value tests establish confidence in foundational functions.

17

Overfit a Tiny Dataset

One of the strongest debugging tests:

Can the model memorize a tiny training dataset?

For example:

8 samples

with enough capacity.

Temporarily ignore generalization.

If the loss cannot become small at all, investigate:

data
labels
architecture
loss
gradient
optimizer
learning rate

A model that cannot fit a trivially small dataset may have an implementation problem.

This is a debugging strategy, not a statement that overfitting is desirable in production.

18

Train/Test Leakage Checks

For every preprocessing step ask:

Was this fitted using information from the test set?

Examples:

scaler
TF-IDF vocabulary
TF-IDF IDF values
feature selection
imputation statistics
threshold selection
hyperparameters

Correct:

train
 ↓
fit preprocessing
 ↓
transform train/test

Incorrect:

all data
 ↓
fit preprocessing
 ↓
split
19

Time-Series Leakage

For sequential or temporal data:

past → training
future → test

Do not allow future information to enter feature construction.

For example:

future rolling average
future target-derived feature
future normalization statistics

can create leakage.

The split strategy must reflect how the model will be used.

20

Label Leakage

A feature can accidentally encode the target.

Example:

post-outcome status

used to predict:

the outcome itself

The model may achieve excellent metrics while solving the wrong problem.

Always ask:

Would this feature genuinely be available at prediction time?

21

Evaluation Protocol

Never report:

"accuracy = 97%"

alone.

Record:

dataset
split
seed
preprocessing
model
hyperparameters
metric
test-set protocol

For classification, where relevant:

accuracy
precision
recall
F1
ROC-AUC
confusion matrix

For regression:

MSE
MAE
R²

For RL:

mean return
success rate
episode length
seed variability

For autoencoders:

reconstruction loss
held-out reconstruction quality

For GANs:

training diagnostics
sample quality
diversity
visual inspection
22

Metrics Must Match the Question

Do not choose a metric because it produced the nicest number.

Start with:

What is the cost of errors?

Examples:

medical screening
→ recall may matter strongly

spam filtering
→ precision may matter strongly

balanced binary classification
→ accuracy may be useful

imbalanced classification
→ F1 / PR-oriented analysis may matter

regression
→ MAE vs MSE depends on error sensitivity

Metric choice is part of problem formulation.

23

Confusion-Matrix Sanity Check

Given:

TP
FP
TN
FN

verify:

\[ N=TP+FP+TN+FN. \]

Then:

\[ Precision= \frac{TP}{TP+FP} \]
\[ Recall= \frac{TP}{TP+FN}. \]

If a metric looks surprising, go back to the counts.

The confusion matrix is the ground-level representation from which many classification metrics are derived.

24

Threshold Debugging

Separate:

model score

from:

decision threshold

For example:

PYTHON
scores = model.predict_proba(
    X_test
)[:, 1]

for threshold in [
    0.3,
    0.5,
    0.7,
]:
    pred = (
        scores >= threshold
    ).astype(int)

If precision/recall changes dramatically, that may be entirely expected.

Do not blame the model until you separate:

ranking quality

from:

decision policy

Configuration Over Hard-Coded Values

Instead of scattering:

PYTHON
64
0.001
5
42

throughout the notebook, define:

PYTHON
CONFIG = {
    "seed": 42,
    "batch_size": 64,
    "learning_rate": 1e-3,
    "epochs": 5,
}

Then use:

PYTHON
CONFIG["learning_rate"]

This makes experiments easier to compare and reproduce.

30

Separate Data, Model and Training

A clean notebook structure:

01_imports
02_config
03_seed
04_data
05_preprocessing
06_model
07_loss
08_optimizer
09_train
10_evaluate
11_visualize
12_save_artifacts

This makes debugging and rerunning easier.

31

Avoid Hidden Notebook State

A classic notebook problem:

Cell 20 depends on Cell 7
Cell 7 was modified
but not rerun

Then the notebook displays stale results.

Better:

Restart kernel
Run all

before considering an experiment final.

For important experiments, execute the pipeline from a clean state.

32

Avoid Accidental Data Mutation

Be careful with in-place operations:

PYTHON
X -= mean

This modifies X.

If another experiment expects the original values, the second experiment silently changes.

Prefer explicit copies when needed:

PYTHON
X_scaled = X.copy()

This is particularly important when comparing preprocessing methods.

33

Experiment Independence

When comparing learning rates:

reset model
reset optimizer
reset seed

as appropriate.

Do not train for:

100 epochs with η=0.1

and then continue the same weights with:

η=0.01

and claim they are independent experiments.

They are not.

34

Model Checkpointing

For PyTorch:

PYTHON
torch.save(
    {
        "model_state": model.state_dict(),
        "optimizer_state": optimizer.state_dict(),
        "epoch": epoch,
        "config": CONFIG,
        "history": history,
    },
    "checkpoint.pt",
)

This is much more useful than saving model weights alone.

35

Prediction Artifact

When evaluating a classifier, save:

sample ID
true label
predicted label
score/probability

For error analysis:

PYTHON
results = pd.DataFrame({
    "true": y_test,
    "pred": predictions,
})

Add scores where available.

This allows you to return to specific errors later.

36

Search Debugging

For BFS/DFS/A*:

record:

current node
frontier
visited/closed set
parent
path cost
heuristic
f(n)

For example:

Expand B
Frontier = [C, D]
g(B) = 2
h(B) = 5
f(B) = 7

A search trace often reveals an ordering bug immediately.

37

A* Debugging

Check:

\[ f(n)=g(n)+h(n). \]

Verify independently:

PYTHON
assert np.isclose(
    f,
    g + h,
)

If optimality behaviour looks wrong, inspect:

heuristic
duplicate-state handling
path-cost updates
priority queue logic
goal test timing

Do not assume the heuristic is responsible.

38

Decision-Tree Debugging

For a from-scratch tree:

record each split:

feature
threshold
parent impurity
left impurity
right impurity
weighted child impurity
gain

Then manually verify one split.

A tree that chooses an unexpected split becomes much easier to debug when the full calculation is visible.

39

Logistic Regression Debugging

Check:

logit
sigmoid
loss
gradient
parameter update

For a binary classifier:

\[ \nabla J= \frac1nX^T(p-y). \]

Use finite differences on a tiny dataset before trusting a hand-written implementation.

40

Linear Regression Debugging

Compare:

gradient descent solution

against:

closed-form least-squares solution

on a small dataset.

If both implementations are correct, the results should agree closely under appropriate conditions.

This is one of the best self-checks in the Unit II codebase.

41

CNN Debugging

Check the full shape chain:

N × C × H × W
      ↓
Conv
      ↓
N × C' × H' × W'
      ↓
Pool
      ↓
N × C' × H'' × W''
      ↓
Flatten
      ↓
N × features
      ↓
Linear

Then calculate \(H'\) and \(W'\) manually.

Never guess the flatten dimension.

42

RNN/LSTM Debugging

Check:

batch
sequence length
feature dimension
hidden dimension
num_layers
directions

Then inspect:

output
h_n
c_n

For sequence-state bugs, print:

t
x_t
h_t

for a tiny sequence.

This turns recurrence into an observable trace.

43

Q-Learning Debugging

For one transition:

s
a
r
s'
Q(s,a)
max Q(s',a')
target
TD error
new Q(s,a)

Verify:

\[ target= r+\gamma\max_{a'}Q(s',a') \]

for non-terminal transitions.

For terminal transitions:

future value contribution
→ excluded

Then compare the code against the manual calculation.

44

Policy-Gradient Debugging

Check:

state
→ logits
→ action probabilities
→ sampled action
→ log_prob
→ reward
→ return
→ policy loss
→ gradient

Common questions:

Does log_prob require gradient?
Are returns aligned with actions?

Residual Analysis

For regression:

\[ e_i=y_i-\hat y_i. \]

Plot:

prediction vs residual

Look for:

systematic curvature
changing spread
outliers

A pattern can reveal model inadequacy that a single MSE number hides.

Compare Against Baselines

Every serious experiment should have a baseline when practical.

Examples:

→ majority-class baseline

regression
→ mean-target predictor

RL
→ random policy

GAN
→ untrained generator / fixed simple baseline

autoencoder
→ trivial baseline reconstruction where meaningful

A model score without a baseline is difficult to interpret.

50

Sanity Checks Before Trusting a Result

Ask:

1. Does the model beat a simple baseline?
2. Does it behave correctly on tiny examples?
3. Is the evaluation leakage-free?
4. Is the result stable across seeds?
5. Do visual/error diagnostics agree with the metric?
6. Does the result survive a clean rerun?

If any answer is “no,” investigate before making strong conclusions.

⚠️ University Lab Viva Trap & Runtime Gotcha
**Silent Shape Broadcasting & Floating Point Invariance:** 1. In NumPy, `(n,)` minus `(n, 1)` broadcasts to `(n, n)` without throwing any error, silently multiplying RAM usage by $n$ and breaking gradient math! Always assert exact shapes! 2. Comparing floating point values with `==` (e.g. `loss == 0.0`) fails due to IEEE 754 precision; always use `np.isclose(a, b, atol=1e-5)` or `np.allclose()`!
