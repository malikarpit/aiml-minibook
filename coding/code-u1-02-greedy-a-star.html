Why This Coding Step Matters

👨‍🏫 Teacher Intuition — Bilingual Implementation Model
Greedy Best-First Search bohot lalchi hota hai—sirf aage dekhta hai ($h(n)$). Jo node goal ke paas lage vahan chala jata hai, chahe pichla rasta kitna bhi lamba aur mehenga kyu na ho! A* Search sabse samajhdar hai: vo dono jodta hai: $f(n) = g(n) + h(n)$. 'Kitna kharcha ho chuka hai' ($g$) plus 'Kitna bacha hai' ($h$). Agar tumhara heuristic $h(n)$ kabhi over-estimate nahi karta (admissible), toh A* hamesha sabse sasta path dhundh nikalega!

BFS and DFS differ mainly in how the frontier chooses its next node.

Now we make that choice more explicit.

BFS
→ shallowest node

DFS
→ deepest node

Greedy
→ smallest h(n)

A*
→ smallest g(n)+h(n)

This gives one of the most reusable ideas in AI search:

The frontier can be ordered by an evaluation function.

The code becomes more general, while the conceptual architecture stays familiar.

03

The Search Problem

Use a weighted graph.

Each edge has a cost.

Example:

B
        /   \
     2 /     \ 2
      /       \
     A         D
      \       /
     1 \     / 1
        \   /
          C
          |
          5
          |
          G

A practical dictionary representation:

PYTHON
graph = {
    "A": [("B", 2), ("C", 1)],
    "B": [("D", 2)],
    "C": [("D", 1), ("G", 5)],
    "D": [("G", 1)],
    "G": [],
}

Here:

A → B costs 2
A → C costs 1
B → D costs 2
C → D costs 1
C → G costs 5
D → G costs 1
04

Why Weighted Costs Matter

BFS only sees depth.

For example:

A → C → G

has 2 steps.

But:

\[ 1+5=6 \]

total cost.

Another route:

A → C → D → G

has 3 steps:

\[ 1+1+1=3. \]

So:

fewer steps
≠
lower cost

This is why cost-aware search is necessary.

05

The Heuristic

A heuristic is an estimate of the remaining cost to reach a goal.

Write:

\[ \boxed{ h(n) } \]

Example:

PYTHON
heuristic = {
    "A": 3,
    "B": 2,
    "C": 2,
    "D": 1,
    "G": 0,
}

For example:

\[ h(D)=1 \]

means:

“From D, I estimate the remaining cost to the goal is 1.”

A heuristic does not need to equal the true cost.

It is an estimate.

06

Best-First Search View

The supplied informed-search lecture frames these methods through an evaluation function:

\[ \boxed{ f(n) } \]

and the frontier selects the node with the smallest evaluation value.

Then:

Greedy

\[ \boxed{ f(n)=h(n) } \]

A*

\[ \boxed{ f(n)=g(n)+h(n) } \]

This is the central code-level abstraction.

07

Why We Need a Priority Queue

A FIFO queue gives:

first inserted → first removed

A LIFO stack gives:

last inserted → first removed

Now we need:

smallest f(n) → first removed

That requires a priority queue.

Python provides:

PYTHON
import heapq

Basic pattern:

PYTHON
heap = []

heapq.heappush(heap, (priority, item))
priority, item = heapq.heappop(heap)

The smallest priority comes out first.

08

Priority Queue Thinking

Suppose the frontier contains:

Node   priority
A        8
B        3
C        5

The next selected node is:

B

because:

\[ 3\lt 5\lt 8. \]

For Greedy:

priority = h(n)

For A*:

priority = g(n) + h(n)
09

Why We Track `g(n)`

A* needs:

\[ g(n) \]

the actual cost already spent getting from the start to \(n\).

For example:

A → C → D

has:

\[ g(D)=1+1=2. \]

So if:

\[ h(D)=1, \]

then:

\[ f(D)=g(D)+h(D)=3. \]

This value determines A*'s frontier priority.

10

Greedy Best-First Search

Greedy ignores accumulated path cost for its priority.

It uses:

\[ \boxed{ f(n)=h(n) } \]

Meaning:

Choose the node that looks closest to the goal.

This is exactly the attraction and weakness of Greedy.

11

Greedy Pseudocode

Greedy(problem):

    frontier ← priority queue ordered by h(n)
    add start

    visited ← empty
    parent[start] ← None

    while frontier not empty:

        current ← remove lowest-h node

        if current is goal:
            return reconstructed path

        if current already visited:
            continue

        mark current visited

        for each successor:
            record parent if appropriate
            push successor with priority h(successor)

    return failure
12

Greedy Implementation

PYTHON
import heapq


def greedy_best_first(graph, start, goal, heuristic):
    frontier = []
    heapq.heappush(frontier, (heuristic[start], start))

    visited = set()
    parent = {start: None}

    while frontier:
        _, current = heapq.heappop(frontier)

        if current in visited:
            continue

        visited.add(current)

        if current == goal:
            return reconstruct_path(parent, goal)

        for neighbor, _ in graph.get(current, []):
            if neighbor not in visited:
                if neighbor not in parent:
                    parent[neighbor] = current

                priority = heuristic[neighbor]
                heapq.heappush(frontier, (priority, neighbor))

    return None

This implementation deliberately leaves path cost out of the priority.

That omission is Greedy's defining behaviour.

With this particular heuristic and tie-breaking convention, the result depends on how equal priorities are ordered. That is an intentional lesson:

Priority ties are part of the implementation behaviour.

Do not assume one universal path whenever two nodes have identical \(h\).

14

Why Greedy Can Be Wrong

Suppose the frontier has:

Node B:
g(B)=20
h(B)=1
f_greedy(B)=1

Node C:
g(C)=2
h(C)=4
f_greedy(C)=4

Greedy chooses B because:

\[ 1\lt 4. \]

But B is already expensive.

If the remaining estimate is poor, Greedy can commit to an expensive route.

A* sees:

\[ f(B)=20+1=21 \]

versus:

\[ f(C)=2+4=6. \]

So A* would choose C.

This is the computational meaning of:

Greedy = future estimate only
A* = past cost + future estimate
15

A* Pseudocode

A*(problem):

    frontier ← priority queue ordered by g(n)+h(n)
    g(start) ← 0
    parent[start] ← None

    push start with priority h(start)

    best_cost ← empty map
    best_cost[start] ← 0

    while frontier not empty:

        current ← remove lowest-f node

        if current is goal:
            return reconstructed path

        for each successor:

            new_cost =
                g(current) + step_cost(current, successor)

            if successor unseen
               or new_cost < best_cost[successor]:

                best_cost[successor] ← new_cost
                parent[successor] ← current

                f = new_cost + h(successor)

                push successor with priority f

    return failure

The new_cost < best_cost[successor] condition is important.

A state may be discovered through multiple paths.

A* must care whether the newly discovered route is cheaper.

16

A* Implementation

PYTHON
import heapq


def astar(graph, start, goal, heuristic):
    frontier = []

    g_cost = {start: 0}
    parent = {start: None}

    heapq.heappush(
        frontier,
        (heuristic[start], start),
    )

    while frontier:
        current_f, current = heapq.heappop(frontier)

        current_g = g_cost[current]

        # Ignore stale priority-queue entries.
        expected_f = current_g + heuristic[current]

        if current_f != expected_f:
            continue

        if current == goal:
            return reconstruct_path(parent, goal)

        for neighbor, step_cost in graph.get(current, []):
            new_g = current_g + step_cost

            if neighbor not in g_cost or new_g < g_cost[neighbor]:
                g_cost[neighbor] = new_g
                parent[neighbor] = current

                new_f = new_g + heuristic[neighbor]

                heapq.heappush(
                    frontier,
                    (new_f, neighbor),
                )

    return None
17

Why Stale Queue Entries Exist

Consider:

A → B cost 8
A → C cost 2
C → B cost 1

Initially:

\[ g(B)=8. \]

Later we discover:

\[ A\to C\to B \]

with cost:

\[ 2+1=3. \]

If the old queue entry with cost 8 remains in the heap, the priority queue now contains information from two different discoveries of B.

Instead of mutating heap elements, a common Python approach is:

push the improved entry and ignore stale entries when they are later popped.

That is the purpose of:

PYTHON
if current_f != expected_f:
    continue

This is an important practical priority-queue pattern.

18

A* Cost Trace

Suppose:

A → C cost 1
C → D cost 1
D → G cost 1

Then:

\[ g(A)=0 \]
\[ g(C)=1 \]
\[ g(D)=2 \]
\[ g(G)=3. \]

If:

\[ h(A)=3,\quad h(C)=2,\quad h(D)=1,\quad h(G)=0 \]

then:

\[ f(A)=0+3=3 \]
\[ f(C)=1+2=3 \]
\[ f(D)=2+1=3 \]
\[ f(G)=3+0=3. \]

This is a perfect heuristic along this route because:

\[ h(n)=h^*(n) \]

for those nodes.

19

Admissibility

The supplied lecture defines an admissible heuristic as one that does not overestimate the actual optimal remaining cost:

\[ \boxed{ h(n)\le h^*(n) } \]

where:

\[ h^*(n) \]

is the true cheapest remaining cost to the goal.

Code-level interpretation

Suppose the real remaining minimum cost is:

7

Then these are admissible:

0
2
5
7

but:

8

is not admissible.

20

Why Admissibility Matters

The A* guarantee depends on assumptions.

Under the standard assumptions used in the lecture:

admissible heuristic
        ↓
A* can safely use heuristic guidance
        ↓
optimality guarantee

The key idea is:

The heuristic is allowed to be optimistic, but not pessimistic in the wrong direction.

More precisely:

It may underestimate the remaining cost, but it must not overestimate it.

21

Heuristic = 0

A very important special case:

\[ \boxed{ h(n)=0 \quad\forall n } \]

Then:

\[ f(n)=g(n). \]

That is Uniform-Cost Search behaviour.

So:

A*
with h = 0
        ↓
f = g
        ↓
UCS

This is a beautiful connection between algorithms.

22

Greedy and A* as One Priority Framework

You can write:

\[ \boxed{ f(n)=\alpha g(n)+\beta h(n) } \]

conceptually, with special choices producing different behaviours.

For this course, the key cases are:

Greedy:
α = 0
β = 1

A*:
α = 1
β = 1

Do not treat this weighted expression as the standard course algorithm definition; it is a conceptual bridge.

The syllabus-relevant formulas remain:

\[ \boxed{ f_{\text{Greedy}}=h } \]

and:

\[ \boxed{ f_{A^*}=g+h. } \]
23

Heuristic Design

A heuristic should help the search identify promising states.

A common way to create one is to solve a relaxed version of the original problem.

The supplied informed-search lecture explicitly presents this idea.

If:

real problem
↓
remove some restrictions
↓
easier problem
↓
solve exactly
↓
cost gives lower bound

then the relaxed-problem cost can be an admissible heuristic.

24

Example: Grid Distance

Suppose a grid permits only four-direction moves:

up
down
left
right

A natural heuristic is Manhattan distance:

\[ \boxed{ h(n) = |x_n-x_g| + |y_n-y_g| } \]

provided each move has unit cost and obstacles can only make the true path longer.

Why is it admissible?

Because no valid route can require fewer unit moves than the required horizontal plus vertical displacement.

This is a pedagogical example of deriving a lower-bound heuristic.

25

Heuristic Testing Function

You can compute:

PYTHON
def is_admissible(
    graph,
    goal,
    heuristic,
    true_costs,
):
    for node, h_value in heuristic.items():
        if h_value > true_costs[node]:
            return False
    return True

This requires true_costs.

For a small graph, you can calculate true optimal costs using a cost-optimal reference search such as Dijkstra/UCS.

The purpose is educational:

candidate heuristic
        ↓
compare against true remaining cost
        ↓
check admissibility
26

Be Careful With “Admissible”

A heuristic being admissible means:

\[ h(n)\le h^*(n). \]

It does not mean:

  • accurate;
  • close to the true cost;
  • always fast;
  • consistent;
  • optimal by itself.

An admissible heuristic can be very weak.

For example:

\[ h(n)=0 \]

is admissible.

But it provides no directional guidance.

27

Weak vs Strong Heuristic

Suppose the true remaining cost is:

\[ h^*(n)=10. \]

Compare:

h₁(n)=1
h₂(n)=7
h₃(n)=10

All are admissible.

But \(h_3\) provides more information.

Under the standard forward-search framing, an admissible heuristic with larger values where valid can dominate a weaker one when it is never less than the weaker heuristic.

The supplied lecture explicitly discusses heuristic dominance and the construction:

\[ h(n)=\max(h_a(n),h_b(n)) \]

when both are admissible.

28

A* Trace Table

Use:

Node   g   h   f=g+h
A      0   6   6
B      2   5   7
C      3   2   5
D      4   3   7
G      8   0   8

A* selects the smallest current \(f\).

So initially:

\[ C \]

is more attractive than:

\[ B. \]

Why?

\[ 5\lt 7. \]

This is how the mathematical formula becomes a concrete priority queue.

29

Greedy Trace Table

Use:

Node   h
A      6
B      5
C      2
D      3
G      0

Greedy sorts only by:

\[ h. \]

Therefore:

G has highest priority
C next
D next
B next
A last

subject to which nodes are actually present in the frontier.

This is why the trace must always distinguish:

all graph nodes

from:

current frontier
30

Greedy Failure Example

Construct:

B -------- G
        /
START - 
        \
          C -------- D -------- G

Suppose:

START → B = 10
B → G = 10

START → C = 1
C → D = 1
D → G = 1

True route costs:

\[ START\to B\to G=20 \]
\[ START\to C\to D\to G=3. \]

Now imagine the heuristic:

\[ h(B)=1 \]

and:

\[ h(C)=3. \]

Greedy prefers B:

\[ 1\lt 3. \]

It can therefore commit toward an expensive solution.

A* sees:

\[ f(B)=10+1=11 \]

and:

\[ f(C)=1+3=4. \]

So A* prefers C.

This is the simplest computational demonstration of why A* uses both \(g\) and \(h\).

32

A* Unit Test — Known Optimal Cost

Create a helper:

PYTHON
def path_cost(graph, path):
    if path is None:
        return float("inf")

    total = 0

    for current, nxt in zip(path, path[1:]):
        for neighbor, cost in graph[current]:
            if neighbor == nxt:
                total += cost
                break
        else:
            raise ValueError("Invalid edge in path.")

    return total

Then:

PYTHON
path = astar(
    graph,
    "A",
    "G",
    heuristic,
)

assert path_cost(graph, path) == 3

This tests the property that matters:

the returned path has the expected least cost for this known problem.

33

Testing Greedy Correctly

Greedy is not generally optimal.

Therefore do not write:

PYTHON
assert path_cost(graph, greedy_path) == optimal_cost

as a universal test.

Instead test:

path exists
path is valid
algorithm terminates
priority rule is respected

Then construct a separate experiment demonstrating that Greedy can produce a suboptimal route.

34

Priority-Queue Tie Breaking

Suppose:

B has h=2
C has h=2

Which one is popped first?

A tuple such as:

PYTHON
(priority, node)

will use node as a secondary comparison in Python's heap ordering.

That means lexical ordering may influence the result.

This is an implementation detail, not an AI theorem.

Better engineering option

Use a counter:

PYTHON
from itertools import count

counter = count()

heapq.heappush(
    frontier,
    (priority, next(counter), node),
)

Now ties are broken by insertion order.

This makes behaviour more explicit and reproducible.

35

A Cleaner Priority Entry

PYTHON
counter = count()

heapq.heappush(

PYTHON

Trace Version — Greedy

PYTHON
def greedy_trace(graph, start, goal, heuristic):
    frontier = []
    counter = count()

    heapq.heappush(
        frontier,
        (heuristic[start], next(counter), start),
    )

    visited = set()
    parent = {start: None}
    trace = []

    while frontier:
        priority, _, current = heapq.heappop(frontier)

        if current in visited:
            continue

        visited.add(current)

        trace.append({
            "node": current,
            "priority": priority,
            "frontier_size": len(frontier),
        })

        if current == goal:
            return reconstruct_path(parent, goal), trace

        for neighbor, _ in graph.get(current, []):
            if neighbor not in visited:
                if neighbor not in parent:
                    parent[neighbor] = current

                heapq.heappush(
                    frontier,
                    (
                        heuristic[neighbor],
                        next(counter),
                        neighbor,
                    ),
                )

    return None, trace

The trace lets you see the priority-based frontier directly.

Trace Version — A*

PYTHON
def astar_trace(graph, start, goal, heuristic):
    frontier = []
    counter = count()

    g_cost = {start: 0}
    parent = {start: None}

    heapq.heappush(
        frontier,
        (heuristic[start], next(counter), start),
    )

    trace = []

    while frontier:
        f_value, _, current = heapq.heappop(frontier)

        current_g = g_cost[current]
        expected_f = current_g + heuristic[current]

        if f_value != expected_f:
            continue

        trace.append({
            "node": current,
            "g": current_g,
            "h": heuristic[current],
            "f": f_value,
            "frontier_size": len(frontier),
        })

        if current == goal:
            return reconstruct_path(parent, goal), trace

        for neighbor, step_cost in graph.get(current, []):
            new_g = current_g + step_cost

            if neighbor not in g_cost or new_g < g_cost[neighbor]:
                g_cost[neighbor] = new_g
                parent[neighbor] = current

                new_f = new_g + heuristic[neighbor]

                heapq.heappush(
                    frontier,
                    (
                        new_f,
                        next(counter),
                        neighbor,
                    ),
                )

    return None, trace

Common Coding Mistakes — Greedy/A*

⚠️ University Lab Viva Trap & Runtime Gotcha
**The Goal-Test-at-Generation Trap:** In BFS, you can goal-test when GENERATING a node. In A* Search, you must NEVER goal-test upon generation! You MUST goal-test ONLY when a node is POPPED from the priority queue! Testing at generation will prematurely return a suboptimal path that happened to be pushed first!

Mistake 1

Using:

PYTHON
g + h

for Greedy.

Wrong.

Greedy uses:

\[ h. \]

Mistake 2

Using only:

PYTHON
h

for A*.

Wrong.

A* uses:

\[ g+h. \]

Mistake 3

Never updating a state's best-known g.

This can miss a cheaper route.

Mistake 4

Confusing edge cost with heuristic.

They are different quantities.

Mistake 5

Assuming an arbitrary heuristic is admissible.

It must satisfy:

\[ h(n)\le h^*(n). \]

Mistake 6

Treating the first discovery of a node as automatically its cheapest path.

That is not generally safe in weighted search.

Mistake 7

Ignoring stale priority-queue entries.

Your heap may contain old entries after a better path is found.

Mistake 8

Interpreting a tie-breaking rule as a theoretical property.

It is usually an implementation detail.
