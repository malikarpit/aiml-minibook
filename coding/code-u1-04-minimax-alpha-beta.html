02

Why Game Search Is Different

👨‍🏫 Teacher Intuition — Bilingual Implementation Model
Minimax ka seedha funda hai: "Main apna best karunga, par ye maante hue ki mera opponent bhi sabse bada master hai aur mera sabse bura chahega." Alpha-Beta Pruning ka magic ye hai ki ye decision ki quality mein 1% bhi compromise kiye bina aadhi branches ko delete kar deta hai. Agar opponent ke paas pehle se ek aisi move hai jo tumhe kam score degi, toh vo is naye raste par kabhi aane hi nahi dega—isiliye aage check karna time waste hai!

A normal route search can ask:

“What path should I take?”

A game involves an opponent.

If you choose:

Move A

the opponent may choose the response that is worst for you.

The supplied lecture therefore states:

An unpredictable opponent means the solution is a strategy specifying a move for every possible opponent reply.

This is why game search is adversarial.

03

The Smallest Useful Game Representation

Before chess, use a tiny deterministic game tree.

A state contains possible child states.

For example:

PYTHON
game_tree = {
    "root": ["A", "B"],
    "A": ["A1", "A2"],
    "B": ["B1", "B2"],
    "A1": [],
    "A2": [],
    "B1": [],
    "B2": [],
}

Terminal utilities:

PYTHON
utility = {
    "A1": 3,
    "A2": 5,
    "B1": 2,
    "B2": 9,
}

Interpretation:

MAX chooses at root
MIN chooses after that
leaf values are final outcomes
04

Game Tree Visual

ROOT (MAX)
                 /           \
              A (MIN)       B (MIN)
              /    \         /    \
            A1      A2      B1      B2
             3       5       2       9

MIN chooses the lower child.

Therefore:

\[ V(A)=\min(3,5)=3 \]

and:

\[ V(B)=\min(2,9)=2. \]

MAX then chooses:

\[ \max(3,2)=3. \]

So the root's optimal value is:

\[ \boxed{3}. \]
05

Minimax Rules

At a terminal state:

\[ \boxed{ V(s)=U(s) } \]

For a MAX state:

\[ \boxed{ V(s)= \max_{a}V(Result(s,a)) } \]

For a MIN state:

\[ \boxed{ V(s)= \min_{a}V(Result(s,a)) } \]

These equations are the computational core.

06

Minimax Pseudocode

MINIMAX(state, player):

    if terminal(state):
        return utility(state)

    if player == MAX:
        value = -∞

        for child in successors(state):
            value = max(
                value,
                MINIMAX(child, MIN)
            )

        return value

    else:
        value = +∞

        for child in successors(state):
            value = min(
                value,
                MINIMAX(child, MAX)
            )

        return value

The recursion alternates:

MAX
 ↓
MIN
 ↓
MAX
 ↓
MIN

Minimax Implementation

PYTHON
def minimax(tree, utility, state, maximizing_player):
    children = tree.get(state, [])

    if not children:
        return utility[state]

    if maximizing_player:
        return max(
            minimax(
                tree,
                utility,
                child,
                False,
            )
            for child in children
        )

    return min(
        minimax(
            tree,
            utility,
            child,
            True,
        )
        for child in children
    )

Run:

PYTHON
value = minimax(
    game_tree,
    utility,
    "root",
    True,
)

print(value)

Expected:

3
08

Choosing the Actual Move

Minimax value alone is not enough.

A game-playing agent needs:

Which child should I choose?

Implement:

PYTHON
def minimax_move(
    tree,
    utility,
    state,
):
    best_move = None
    best_value = float("-inf")

    for child in tree.get(state, []):
        value = minimax(
            tree,
            utility,
            child,
            False,
        )

        if value > best_value:
            best_value = value
            best_move = child

    return best_move, best_value

Run:

PYTHON
move, value = minimax_move(
    game_tree,
    utility,
    "root",
)

print(move, value)

Expected:

A 3
09

Why MAX Chooses A

For:

A → {3,5}

MIN chooses 3.

For:

B → {2,9}

MIN chooses 2.

So MAX compares:

A → 3
B → 2

and chooses A.

This is the essence of adversarial reasoning:

MAX assumes MIN will respond intelligently.
10

Why Minimax Is Not “Choose the Highest Leaf”

A common beginner mistake:

Leaves:
3,5,2,9

and then:

“9 is the best, so choose B.”

Wrong.

MAX does not control both levels.

After MAX chooses B, MIN chooses the worse outcome for MAX:

\[ \min(2,9)=2. \]

This is why the intermediate player labels matter.

11

Minimax Trace

Build a tracing version:

PYTHON
def minimax_trace(
    tree,
    utility,
    state,
    maximizing_player,
    trace=None,
):
    if trace is None:
        trace = []

    children = tree.get(state, [])

    if not children:
        value = utility[state]

        trace.append({
            "state": state,
            "player": "terminal",
            "value": value,
        })

        return value, trace

    player = "MAX" if maximizing_player else "MIN"

    values = []

    for child in children:
        child_value, trace = minimax_trace(
            tree,
            utility,
            child,
            not maximizing_player,
            trace,
        )

        values.append(
            (child, child_value)
        )

    if maximizing_player:
        best_child, value = max(
            values,
            key=lambda item: item[1],
        )
    else:
        best_child, value = min(
            values,
            key=lambda item: item[1],
        )

    trace.append({
        "state": state,
        "player": player,
        "children": values,
        "chosen": best_child,
        "value": value,
    })

    return value, trace

Inspect the trace to see values propagate upward.

12

Recursive Value Flow

Think bottom-up:

Leaves
  ↓
MIN evaluates leaves
  ↓
MAX evaluates MIN values
  ↓
MIN evaluates MAX values
  ↓
...
  ↓
root value

The algorithm is recursive in code but conceptually performs a bottom-up value computation over the game tree.

13

Minimax Complexity

The supplied lecture gives:

\[ \boxed{ O(b^m) } \]

time for minimax and:

\[ \boxed{ O(bm) } \]

space in its depth-first formulation.

Here:

  • \(b\) = branching factor;
  • \(m\) = search depth.

The problem is the exponential growth of possible game sequences.

14

Why Real Games Are Hard

The lecture points out that practical games such as chess have a large branching factor and depth.

So:

one position
↓
many moves
↓
each move has many replies
↓
each reply has many replies
↓
explosion

Even a modest-looking depth becomes computationally enormous.

This motivates pruning and later resource-limited evaluation.

15

Alpha-Beta Pruning

Alpha-beta does not change the minimax result under its standard safe-pruning assumptions.

It changes:

how much of the tree must actually be evaluated.

The lecture states:

Safe: pruning does not affect the final result.

16

Alpha and Beta

The supplied lecture's explanation:

Alpha

\[ \boxed{ \alpha = \text{best value found so far for MAX along the current path} } \]

Beta

\[ \boxed{ \beta = \text{best bound found so far for MIN along the current path} } \]

The pruning condition is:

\[ \boxed{ \alpha\ge\beta \Rightarrow \text{prune} } \]

This is the critical formula.

17

Alpha-Beta Intuition

Suppose MAX already has a guaranteed option worth:

\[ 5. \]

So:

\[ \alpha=5. \]

Now MAX explores another branch.

At a MIN node, one child produces:

\[ 3. \]

MIN can already force this branch down to 3.

Since:

\[ 3\lt 5, \]

MAX would never choose this branch over the existing option worth 5.

Therefore the remaining children of that MIN node cannot change MAX's final decision.

They can be pruned.

18

Alpha-Beta Pseudocode

ALPHABETA(state, depth, α, β, maximizing):

    if terminal:
        return utility(state)

    if MAX:
        value = -∞

        for child:
            value = max(
                value,
                ALPHABETA(
                    child,
                    α,
                    β,
                    MIN
                )
            )

            α = max(α, value)

            if α >= β:
                break

        return value

    else:
        value = +∞

        for child:
            value = min(
                value,
                ALPHABETA(
                    child,
                    α,
                    β,
                    MAX
                )
            )

            β = min(β, value)

            if α >= β:
                break

        return value
19

Alpha-Beta Implementation

PYTHON
def alpha_beta(
    tree,
    utility,
    state,
    maximizing_player,
    alpha=float("-inf"),
    beta=float("inf"),
):
    children = tree.get(state, [])

    if not children:
        return utility[state]

    if maximizing_player:
        value = float("-inf")

        for child in children:
            value = max(
                value,
                alpha_beta(
                    tree,
                    utility,
                    child,
                    False,
                    alpha,
                    beta,
                ),
            )

            alpha = max(alpha, value)

            if alpha >= beta:
                break

        return value

    value = float("inf")

    for child in children:
        value = min(
            value,
            alpha_beta(
                tree,
                utility,
                child,
                True,
                alpha,
                beta,
            ),
        )

        beta = min(beta, value)

        if alpha >= beta:
            break

    return value

Instrumented Minimax

PYTHON
def minimax_count(
    tree,
    utility,
    state,
    maximizing_player,
    stats,
):
    children = tree.get(state, [])

    if not children:
        stats["leaf_evaluations"] += 1
        return utility[state]

    values = [
        minimax_count(
            tree,
            utility,
            child,
            not maximizing_player,
            stats,
        )
        for child in children
    ]

    if maximizing_player:
        return max(values)

    return min(values)
23

Instrumented Alpha-Beta

PYTHON
def alpha_beta_count(
    tree,
    utility,
    state,
    maximizing_player,
    alpha,
    beta,
    stats,
):
    children = tree.get(state, [])

    if not children:
        stats["leaf_evaluations"] += 1
        return utility[state]

    if maximizing_player:
        value = float("-inf")

        for child in children:
            value = max(
                value,
                alpha_beta_count(
                    tree,
                    utility,
                    child,
                    False,
                    alpha,
                    beta,
                    stats,
                ),
            )

            alpha = max(alpha, value)

            if alpha >= beta:
                stats["prunes"] += 1
                break

        return value

    value = float("inf")

    for child in children:
        value = min(
            value,
            alpha_beta_count(
                tree,
                utility,
                child,
                True,
                alpha,
                beta,
                stats,
            ),
        )

        beta = min(beta, value)

        if alpha >= beta:
            stats["prunes"] += 1
            break

    return value

    "leaf_evaluations": 0,
    "prunes": 0,

24

Why Move Ordering Matters

The supplied lecture explicitly states:

Good move ordering improves the effectiveness of pruning.

This is extremely important.

Alpha-beta can only prune a branch after sufficient bounds have already been established.

If good moves are examined early:

strong bound early
↓
more α/β cutoffs
↓
more pruning

Poor ordering can produce much less pruning.

25

Best-Case Idea

The lecture gives the idealized perfect-ordering complexity:

\[ \boxed{ O(b^{m/2}) } \]

This is dramatically better than:

\[ O(b^m). \]

The interpretation is not:

“Alpha-beta always runs in \(b^{m/2}\).”

It is:

Under ideal move ordering, the amount of search can be reduced to that order in the standard analysis.

ordering B

where the child order differs.

Measure:

The minimax result should remain the same.

But alpha-beta's search effort can change.

This turns an abstract lecture statement into a measurable experiment.

28

Why Can We Prune Without Knowing Exact Value?

This is a crucial reasoning skill.

Suppose MIN has already found:

\[ 3. \]

So MIN can guarantee:

\[ V\le3. \]

MAX already has another route worth:

\[ 5. \]

MAX therefore will never choose the branch whose best possible value is at most 3.

We do not need the branch's exact final value.

A bound is sufficient.

This is the deeper idea behind alpha-beta.

29

Alpha-Beta Is Not an Approximation

A common misunderstanding:

“Alpha-beta gets a rough answer faster.”

Wrong.

Under the standard deterministic perfect-play assumptions, alpha-beta returns the same minimax value.

It is a computational optimization.

Minimax:
evaluate relevant tree

Alpha-beta:
prove some branches irrelevant
+
evaluate the rest
30

Comparison — Minimax vs Alpha-Beta

Property Minimax Alpha-Beta
Final value optimal minimax value same value
Pruning no yes
Needs alpha/beta no yes
Sensitive to move ordering indirectly strongly
Basic time \(O(b^m)\) worst case can remain \(O(b^m)\)
Ideal ordering — \(O(b^{m/2})\)
Main purpose correctness reduce unnecessary computation

Applying to Tic-Tac-Toe

Tic-tac-toe is small enough for complete search.

A state can be:

(
    cell0,
    cell1,
    ...
    cell8,
)

Example:

(

    None, "X", None,

Legal actions:

all empty cells

Terminal conditions:

X wins
O wins

Utility from X's perspective:

Then minimax can choose the optimal move.

TERMINAL-TEST
      ↓

That is not the same algorithm as exact minimax over the full game tree.

Simple Evaluation Function Example

For a toy game, define:

PYTHON
def evaluate(state):
    score = 0

    score += 3 * state["material_advantage"]
    score += 1 * state["mobility_advantage"]

    return score

The exact features depend on the game.

The important idea is:

A non-terminal position needs an estimated desirability score when search is cut off.

Horizon Effect

The supplied lecture discusses the horizon effect:

An undesirable event can be delayed just beyond the search horizon instead of truly avoided.

Coding experiment:

max_depth = 2

may make a move look good.

Increase:

max_depth = 4

and the preferred move may change.

This is why resource-limited search is approximate.

The lecture introduces quiescence for unstable positions.

The basic idea:

reached cutoff
    ↓

    ↓

    ↓

Common Coding Mistakes

⚠️ University Lab Viva Trap & Runtime Gotcha
**Alpha-Beta Condition & Role Confusion:** In code, MAX updates `alpha = max(alpha, eval)`, while MIN updates `beta = min(beta, eval)`. The cutoff condition is `if beta <= alpha: break`. Swapping `alpha` and `beta` updates, or using `<` instead of `<=`, destroys pruning efficiency or causes incorrect moves!

Mistake 1

Using MAX at every level.

Then you no longer have minimax.

Mistake 2

Returning the highest leaf value.

Intermediate MIN nodes matter.

Mistake 3

Changing alpha-beta's output due to pruning.

Pruning should preserve the minimax result.

Mistake 4

Initializing alpha/beta incorrectly.

Standard initialization:

\[ \alpha=-\infty, \qquad \beta=+\infty. \]

Mistake 5

Mixing up alpha and beta.

Remember:

α → MAX's best known lower bound
β → MIN's best known upper bound

Mistake 6

Forgetting the cutoff condition:

\[ \alpha\ge\beta. \]

Mistake 7

Assuming move ordering cannot affect performance.

It can affect pruning substantially.

Mistake 8

Assuming alpha-beta approximates minimax.

It is exact under the standard assumptions.

Final Memory Sheet

MINIMAX

MAX → maximize
MIN → minimize

terminal → utility
MAX → max(children)
MIN → min(children)

Alpha-beta:

α = MAX's current best bound
β = MIN's current best bound

α ≥ β
   ↓
prune

Complexity:

\[ \boxed{ \text{Minimax }O(b^m) } \]

Idealized perfect ordering:

\[ \boxed{ \alpha\text{-}\beta\ O(b^{m/2}) } \]

The central principle:

Alpha-beta does not change the answer. It avoids computations that cannot change the answer.
