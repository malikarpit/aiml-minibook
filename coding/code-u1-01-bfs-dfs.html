03

Problem Setup

We will represent a graph using an adjacency dictionary.

Example:

PYTHON
graph = {
    "A": ["B", "C"],
    "B": ["D", "E"],
    "C": ["F", "G"],
    "D": [],
    "E": [],
    "F": [],
    "G": [],
}

Visually:

A
         /   \
        B     C
       / \   / \
      D   E F   G

Assume:

  • graph edges represent possible actions;
  • each listed edge has equal cost;
  • the goal is a node such as "G";
  • child order is left-to-right according to the list.

This gives us a hand-checkable environment.

04

Why This Representation?

The dictionary:

PYTHON
graph[node] = successors

makes the problem definition explicit.

For example:

PYTHON
graph["B"]

returns:

PYTHON
["D", "E"]

meaning:

From B, the available next states are D and E.

The algorithm should not care how the original problem generated that dictionary.

That separation is important:

Problem representation
        ↓
Search algorithm

The search procedure can therefore be reused for:

  • mazes;
  • route finding;
  • puzzles;
  • state transitions;
  • game states;
  • scheduling states.
05

Search Node vs State

In a simple teaching implementation, a node can be represented by its state name.

But real search systems often need more information:

Search node
├── state
├── parent
├── action
├── path cost
└── depth

Why?

Suppose the algorithm reaches:

G

It must know:

“How did I get here?”

A parent mapping lets us reconstruct the path.

This file starts with the simple representation and then makes the parent relation explicit.

06

BFS — Core Idea

The supplied lecture defines BFS as:

Expand the shallowest unexpanded node.

Implementation:

Use a FIFO queue, so newly generated successors go to the back.

Source: lecture-basic-search.pdf, Breadth-First Search slides 24–25.

Memory hook:

\[ \boxed{\text{BFS}=\text{shallowest first}=\text{FIFO}} \]
07

BFS Pseudocode

Before Python, write the algorithm:

BFS(graph, start, goal):

    create an empty FIFO frontier
    add start to frontier

    create visited set
    create parent map
    parent[start] = None

    while frontier is not empty:

        current = remove front of frontier

        if current == goal:
            reconstruct path
            return path

        mark current visited

        for each neighbor of current:

            if neighbor has not been seen:
                record current as neighbor's parent
                add neighbor to frontier

    return failure

Important implementation choice

There are different conventions for when a node becomes “visited” or “seen.”

For a clean graph-search implementation, we will usually mark a node as discovered when it enters the frontier rather than waiting until removal.

Why?

It prevents the same state from being inserted many times by different parents.

08

BFS Data Structure

Python's collections.deque is a suitable queue:

PYTHON
from collections import deque

Basic operations:

PYTHON
queue.append(x)      # add to back
queue.popleft()      # remove from front

This matches FIFO behaviour.

Do not use:

PYTHON
list.pop(0)

for a large queue because removing from the front of a Python list requires shifting elements.

The algorithmic idea is FIFO either way, but the data structure affects implementation efficiency.

09

BFS — First Implementation

PYTHON
from collections import deque


def bfs(graph, start, goal):
    queue = deque([start])

    visited = {start}
    parent = {start: None}

    while queue:
        current = queue.popleft()

        if current == goal:
            return reconstruct_path(parent, goal)

        for neighbor in graph.get(current, []):
            if neighbor not in visited:
                visited.add(neighbor)
                parent[neighbor] = current
                queue.append(neighbor)

    return None

We have referenced a helper:

PYTHON
reconstruct_path(...)

which we will write next.

10

Path Reconstruction

Suppose:

A → B → E → G

The parent map is:

PYTHON
{
    "A": None,
    "B": "A",
    "E": "B",
    "G": "E",
}

Start at:

G

then follow parents:

G ← E ← B ← A

Reverse it:

A → B → E → G

Implementation:

PYTHON
def reconstruct_path(parent, goal):
    path = []

    current = goal

    while current is not None:
        path.append(current)
        current = parent[current]

    path.reverse()
    return path

This small helper is one of the most reusable patterns in search programming.

11

Full BFS Example

PYTHON
from collections import deque


def reconstruct_path(parent, goal):
    path = []
    current = goal

    while current is not None:
        path.append(current)
        current = parent[current]

    path.reverse()
    return path


def bfs(graph, start, goal):
    queue = deque([start])

    visited = {start}
    parent = {start: None}

    while queue:
        current = queue.popleft()

        if current == goal:
            return reconstruct_path(parent, goal)

        for neighbor in graph.get(current, []):
            if neighbor not in visited:
                visited.add(neighbor)
                parent[neighbor] = current
                queue.append(neighbor)

    return None

Test:

Manual BFS Trace

Start:

frontier = [A]
seen = {A}

Expand A:

remove A
add B, C

frontier = [B, C]
seen = {A, B, C}

Expand B:

remove B
add D, E

frontier = [C, D, E]

Expand C:

remove C
add F, G

frontier = [D, E, F, G]

The goal G is now waiting in the frontier.

14

BFS Goal-Test Convention

There are two common conceptual conventions:

Test on removal

pop node
↓
goal?
↓
expand

Test on generation

generate successor
↓
goal?

Both can be implemented correctly, but the observed trace can differ slightly.

For this Coding Book, the teaching implementation uses:

goal test when the node is removed from the frontier.

The key is to state the convention rather than silently changing it between examples.

15

BFS Why It Finds a Shallow Solution First

Because the queue preserves insertion order:

Depth 0
  ↓
Depth 1
  ↓
Depth 2
  ↓
Depth 3

The algorithm exhausts shallower layers before moving to deeper layers.

So if all steps have equal cost:

\[ \text{path cost}=\text{number of steps}. \]

Therefore:

\[ \boxed{ \text{shallowest solution} = \text{least-cost solution} } \]

under the equal-step-cost assumption.

This is the mathematical reason behind BFS's standard optimality condition from the lecture.

16

BFS Complexity

The supplied lecture gives:

\[ \boxed{ O(b^{d+1}) } \]

for standard BFS time analysis and:

\[ \boxed{ O(b^{d+1}) } \]

for space because many frontier nodes must remain in memory.

Here:

  • \(b\) = branching factor;
  • \(d\) = depth of the shallowest solution.

Coding interpretation

Large branching factor + large depth:

→ enormous frontier
→ high memory usage

This is why BFS's memory consumption is its famous weakness.

17

BFS Unit Test

Use a known graph:

PYTHON
def test_bfs_finds_shallow_path():
    graph = {
        "A": ["B", "C"],
        "B": ["D"],
        "C": ["G"],
        "D": ["G"],
        "G": [],
    }

    path = bfs(graph, "A", "G")

    assert path == ["A", "C", "G"]

Why should C be selected?

A → C → G = 2 steps
A → B → D → G = 3 steps

BFS returns the shallower path.

20

BFS Edge Case — Cycle

Consider:

A → B → C
↑       |
└───────┘

Without duplicate detection:

A → B → C → A → B → C → ...

The algorithm can loop.

With:

PYTHON
visited = {start}

and marking states when discovered, each state is added at most once.

This is the difference between a toy tree-search implementation and a safer graph-search implementation.

22

DFS — Core Idea

The supplied lecture defines DFS as:

Expand the deepest unexpanded node.

Implementation:

Use a LIFO queue/stack, putting successors at the front.

Source: lecture-basic-search.pdf, Depth-First Search slides 29 onward.

Memory hook:

\[ \boxed{ \text{DFS}=\text{deepest first}=\text{LIFO} } \]
23

DFS Pseudocode

DFS(graph, start, goal):

    create an empty LIFO frontier
    push start

    create visited set
    create parent map
    parent[start] = None

    while frontier is not empty:

        current = pop frontier

        if current == goal:
            reconstruct path
            return path

        if current is already visited:
            continue

        mark current visited

        for each neighbor in appropriate order:
            if neighbor has not been visited:
                record parent
                push neighbor

    return failure

There is an implementation detail here:

The order in which successors are pushed determines which branch becomes the next deepest branch.

24

DFS Data Structure

Python list:

PYTHON
stack = []

Push:

PYTHON
stack.append(x)

Pop top:

PYTHON
stack.pop()

This gives LIFO behaviour.

Example:

push A
push B
push C

stack:
[A, B, C]

pop → C

The newest item leaves first.

25

DFS — First Implementation

PYTHON
def dfs(graph, start, goal):
    stack = [start]

    visited = set()
    parent = {start: None}

    while stack:
        current = stack.pop()

        if current in visited:
            continue

        visited.add(current)

        if current == goal:
            return reconstruct_path(parent, goal)

        for neighbor in reversed(graph.get(current, [])):
            if neighbor not in visited:
                if neighbor not in parent:
                    parent[neighbor] = current
                stack.append(neighbor)

    return None

Why reversed(...)?

Suppose:

PYTHON
graph["A"] = ["B", "C"]

We want B to be explored before C under left-to-right teaching order.

Because a stack is LIFO, push:

C
B

so that:

B

is popped first.

This is a very common implementation detail.

26

DFS Trace

Using:

A
├── B
│   ├── D
│   └── E
└── C
    ├── F
    └── G

Start:

stack = [A]

Pop A:

stack receives C then B
stack = [C, B]

Pop B:

stack = [C, E, D]

Pop D:

stack = [C, E]

Pop E:

stack = [C]

Only then does DFS move to C.

This is the fundamental difference from BFS.

28

DFS and the Deep-Path Problem

Consider:

A
├── B
│   └── C
│       └── D
│           └── E
│               └── ...
└── GOAL

DFS can keep following:

A → B → C → D → E → ...

and never return to explore the right branch if the left path is infinite.

The lecture identifies this as a reason DFS is not complete in general.

Coding lesson

A search implementation is not only about data structures.

You must understand:

state-space structure
        +
algorithm assumptions
29

DFS and Cycles

Example:

A → B
↑   |
|   ↓
D ← C

A naive DFS can repeatedly traverse the cycle.

The graph-search version uses a visited set:

PYTHON
visited = set()

to avoid repeatedly expanding the same state.

Important nuance

“Visited” is a state-level concept.

In richer search problems, reaching the same apparent state with different path-cost or resource information may require a more careful state definition.

Do not oversimplify the meaning of “state.”

30

DFS Complexity

The supplied lecture gives standard DFS analysis in terms of the maximum depth \(m\):

\[ \boxed{ O(b^m) } \]

for time, with standard depth-first space:

\[ \boxed{ O(bm) } \]

under the lecture's search-tree framing.

Here:

  • \(b\) = branching factor;
  • \(m\) = maximum depth of the state space.

Key comparison

BFS:
memory grows with solution depth

DFS:
memory grows primarily with current depth

This is why DFS can be dramatically more memory-efficient.

31

DFS Unit Test

PYTHON
def test_dfs_finds_a_path():
    graph = {
        "A": ["B", "C"],
        "B": ["D", "E"],
        "C": ["F", "G"],
        "D": [],
        "E": [],
        "F": [],
        "G": [],
    }

    path = dfs(graph, "A", "G")

    assert path == ["A", "C", "G"] or path is not None

Be careful here.

A DFS implementation does not guarantee the shallowest path.

Therefore a stronger correctness test is often:

“The returned path is valid.”

rather than:

“The returned path must equal the BFS path.”

This distinction is essential.

32

Testing Path Validity

Write a general helper:

PYTHON
def is_valid_path(graph, path, start, goal):
    if path is None:
        return False

    if not path:
        return False

    if path[0] != start:
        return False

    if path[-1] != goal:
        return False

    for a, b in zip(path, path[1:]):
        if b not in graph.get(a, []):
            return False

    return True

Now test:

PYTHON
path = dfs(graph, "A", "G")

assert is_valid_path(graph, path, "A", "G")

This is a better software-engineering style test because it checks the required property rather than one incidental traversal order.

Traceable DFS

During debugging, it is useful to see the stack.

A tracing version:

PYTHON
def dfs_trace(graph, start, goal):
    stack = [start]
    visited = set()
    parent = {start: None}

    trace = []

    while stack:
        current = stack.pop()

        trace.append({
            "popped": current,
            "stack_after_pop": stack.copy(),
        })

        if current in visited:
            continue

        visited.add(current)

        if current == goal:
            return reconstruct_path(parent, goal), trace

        for neighbor in reversed(graph.get(current, [])):
            if neighbor not in visited:
                if neighbor not in parent:
                    parent[neighbor] = current
                stack.append(neighbor)

    return None, trace

Then inspect:

PYTHON
path, trace = dfs_trace(graph, "A", "G")

for step in trace:
    print(step)

This makes the abstract LIFO rule visible.

A natural choice when:

+

+

45

Important Difference: Search vs Traversal

These algorithms are often introduced as graph traversal methods, but in AI they are used for state-space search.

Traversal question:

“In what order will I visit graph nodes?”

Search question:

“Can I find a goal state, and what solution path should I return?”

The second requires:

  • goal testing;
  • parent/path information;
  • state representation;
  • solution reconstruction.

That is why this Coding Book implements search, not merely a traversal printout.

46

Common Coding Mistakes

⚠️ University Lab Viva Trap & Runtime Gotcha
**Graph Search vs Tree Search Trap:** In Tree Search, states can be visited multiple times. In Graph Search, you MUST maintain an `explored` set! If you forget the `explored` set on a graph with cycles (e.g. A-B-A), DFS will enter infinite recursion and throw `RecursionError: maximum recursion depth exceeded`!

Mistake 1 — Using pop(0) for a large BFS queue

This can make the implementation inefficient.

Prefer:

PYTHON
deque.popleft()

Mistake 2 — Marking visited too late

The same state can enter the queue repeatedly.

Mistake 3 — Forgetting cycles

A graph can loop forever without duplicate handling.

Mistake 4 — Assuming DFS returns the shortest path

It does not generally do so.

Mistake 5 — Assuming traversal order is universal

Neighbour ordering matters.

Mistake 6 — Treating a state name as sufficient for every problem

Real search states may need richer representations.

Mistake 7 — Testing only one exact DFS path

Many valid DFS implementations can produce different valid paths.

Mistake 8 — Hiding the algorithm inside a library call

That defeats the from-scratch learning objective.

Extension — Weighted Graph Thought Experiment

Suppose:

A → B → G
cost = 1 + 1

A → C → D → G
cost = 0.2 + 0.2 + 0.2

BFS prefers the second-level goal path based on depth.

But the cheaper route has more steps.

This demonstrates why:

\[ \boxed{ \text{fewest steps} \neq \text{least cost} } \]

when edge costs differ.

The supplied lecture uses this distinction to motivate Uniform-Cost Search.
