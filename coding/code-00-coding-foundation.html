CODE-00 — AI/ML Coding Book Foundation and Implementation System

Coding Book — AI & Machine Learning

Course boundary: Faculty of Technology, University of Delhi — DSC-14 Artificial Intelligence and Machine Learning

Role of this book: Turn the concepts taught in the Main Book into executable programs, experiments, tests, traces, visualizations, and small implementation projects.

Companion relationship:

> Main Book      → understand the concept
> Math Companion → understand the mathematics
> Coding Book    → implement and experiment
> Exam Book      → recall and write under exam conditions
>

Important: The Coding Book is not a replacement for the Main Book. Do not learn an algorithm only by copying code. Every implementation begins with the problem, representation, pseudocode, trace, and expected behaviour.

02

What This Book Will Teach

👨‍🏫 Teacher Intuition — Bilingual Implementation Model
Code copy-paste karke run karna 'learning' nahi hota. Asli engineer aur AI researcher vo hota hai jo pehle problem aur data structure ko dimaag mein imagine karta hai, paper par algorithm trace karta hai, aur phir clean, modular, zero-black-box code likhta hai. Coding Lab ka golden rule hai: **"No black boxes until you build the box yourself!"**

The Coding Book should make you capable of answering:

“I understand what this algorithm does. Can I actually build it?”

For each major algorithm/model, the expected progression is:

Level C0 — Recognize

Identify the algorithm from its description.

Level C1 — Read

Understand existing implementation code.

Level C2 — Modify

Change a parameter or small section safely.

Level C3 — Implement

Write the core algorithm from pseudocode without copying a finished solution.

Level C4 — Test

Verify edge cases, expected outputs, and invariants.

Level C5 — Visualize

Inspect what the algorithm is doing.

Level C6 — Compare

Compare the from-scratch version with a mature library implementation.

Level C7 — Explain

Defend the design, complexity, assumptions, failure cases, and results.

Target

For university practicals:

\[ \boxed{\text{C3–C4}} \]

For strong engineering ability:

\[ \boxed{\text{C5–C6}} \]

For project/research readiness:

\[ \boxed{\text{C7}} \]
03

The Coding Book Does Not Mean “Copy and Run”

A dangerous learning pattern is:

Open notebook
↓
Copy code
↓
Run
↓
See output
↓
Assume learned

That produces very weak transfer.

Instead use:

Read problem
↓
Draw representation
↓
Write pseudocode
↓
Predict behaviour
↓
Implement
↓
Test
↓
Trace
↓
Debug
↓
Explain output
↓
Only then use library implementation

The implementation is the last visible layer of understanding, not the first.

06

Universal Practical Template

Every substantial coding chapter follows this structure.

1. Coding objective

What are we implementing?

2. Learning target

What should you be able to implement from memory?

3. Required environment

Python version, libraries, hardware assumptions, and expected runtime.

4. Input representation

What do the data structures look like?

5. Problem setup

Use a small hand-checkable example before a large dataset.

6. Algorithm idea

Explain the implementation logic in plain English.

7. Pseudocode

Pseudocode must come before executable implementation.

8. From-scratch implementation

Implement the essential logic without hiding it inside a high-level library.

9. Line-by-line logic map

Explain the important portions rather than commenting every trivial syntax element.

10. Manual trace

Show the state changing step by step.

11. Tests

At minimum:

  • normal case;
  • boundary case;
  • edge/failure case.

12. Complexity

State time and space complexity where meaningful.

13. Visualization

Show a graph, decision boundary, loss curve, search frontier, trajectory, confusion matrix, or other useful visual.

14. Library implementation

Only after the from-scratch implementation.

15. Compare

Compare:

from scratch
vs
library

in terms of:

  • abstraction;
  • correctness;
  • performance;
  • readability;
  • flexibility.

16. Debugging lab

Show at least one realistic mistake and how to diagnose it.

17. Experiment

Change one or two variables and observe what changes.

18. Interpretation

Explain what the result actually means.

19. Active recall

Close the notebook and answer implementation questions.

20. Coding challenge

Write a small extension without copying the original implementation.

07

What “From Scratch” Means

From-scratch does not mean rebuilding Python.

It means implementing the algorithm's essential logic yourself.

Good

PYTHON
def bfs(graph, start):
    ...

where the queue handling, visited tracking, and traversal logic are yours.

Not enough

PYTHON
from some_library import bfs

followed by a one-line call.

The library version is useful later for comparison, but it is not the learning implementation.

08

What Libraries Are Allowed?

Libraries are tools, not shortcuts around understanding.

Typical tools in this book may include:

Purpose Typical library
Numerical arrays NumPy
Tables / datasets pandas
Visualization Matplotlib
Classical ML scikit-learn
Deep learning PyTorch
NLP scikit-learn / PyTorch / standard Python tools
Image processing Pillow / torchvision where required
Graph/search visualizations Matplotlib / simple Python structures

The exact package set should remain minimal.

Do not install a huge stack merely because it exists.

09

Reproducibility Standard

Every substantial experiment should make the important sources of randomness explicit.

For example:

PYTHON
import numpy as np

rng = np.random.default_rng(42)

or an equivalent framework-specific seed.

A reproducible experiment records:

dataset
↓
preprocessing
↓
train/validation/test split
↓
random seed
↓
model configuration
↓
training settings
↓
evaluation metric
↓
result

A result that cannot be reproduced is much less useful as a learning artifact.

10

Data Handling Rule

Never silently leak test information into training.

The safe conceptual workflow is:

Raw dataset
    ↓
Split
 ┌──┴───────────────┐
 ↓                  ↓
Train              Test
 ↓
fit preprocessing
 ↓
train model
 ↓
evaluate on test

For validation-based model selection:

Train
Validation
Test

The test set should remain untouched until final evaluation.

11

Shape Discipline

A large fraction of practical ML bugs are shape bugs.

For every array, know its shape.

Example:

X → (n_samples, n_features)
y → (n_samples,)

A neural-network layer might use:

W → (n_out, n_in)
b → (n_out,)
x → (n_in,)

Then:

W @ x → (n_out,)

Do not proceed until dimensions make sense.

12

Assertions Are Part of Learning

Use assertions to catch incorrect assumptions early.

Example:

PYTHON
assert X.ndim == 2
assert len(X) == len(y)
assert not np.isnan(X).any()

The exact assertions depend on the experiment.

The philosophy is:

Make important assumptions executable.

13

Testing Philosophy

Tests should answer:

“Did I implement the intended algorithm?”

Not merely:

“Did Python run?”

Example categories:

Example test

A small known input with an expected answer.

Boundary test

An input near an algorithmic edge.

Empty/minimal test

For example:

one node
one feature
one sample
empty path

where applicable.

Failure test

An intentionally invalid input or impossible situation.

14

Traceability

Every important implementation should make its internal state observable.

Examples:

Search

step
current node
frontier
visited
parent

Linear regression

iteration
weights
loss
gradient

Neural network

layer
activation
loss
gradient

Q-learning

state
action
reward
next state
old Q
new Q

Without a trace, debugging becomes much harder.

16

Debugging Method

When code fails, do not randomly change lines.

Use:

Observe
↓
Classify
↓
Localize
↓
Test hypothesis
↓
Fix
↓
Re-run
↓
Add regression test

Error categories

Syntax error

Python cannot parse the code.

Shape error

Arrays/tensors have incompatible dimensions.

Type error

The object is not the expected type.

Logic error

The program runs but gives the wrong result.

Numerical error

The mathematics is correct in principle but unstable, overflowing, underflowing, or poorly scaled.

Data error

Input assumptions are wrong.

Evaluation error

The code is technically correct but the experimental methodology is flawed.

That last category matters enormously in ML.

17

Numerical ML Debugging

When a model behaves strangely, inspect:

NaN?
Inf?
Exploding loss?
Constant loss?
Weights all zero?
Weights enormous?
Predictions constant?
Train ≫ test?
Test ≫ train?

For gradient-based models, also inspect:

\[ \|\nabla J\| \]

and parameter magnitudes.

18

Core Engineering Rules

Rule 1

Start small.

2–5 examples

before:

100,000 examples

Rule 2

Know the expected result before executing.

Rule 3

Prefer explicit intermediate variables while learning.

Rule 4

Vectorize only after understanding the scalar logic.

Rule 5

Separate data, model, training, and evaluation logic.

Rule 6

Keep experiments reproducible.

Rule 7

Use tests to protect working code.

Rule 8

Never interpret an ML result without checking how it was obtained.

19

Pseudocode Before Code

For a search algorithm:

Create frontier
Mark start
While frontier not empty:
    remove next state
    if goal:
        return solution
    generate successors
    add valid successors
return failure

For gradient descent:

Initialize parameters
Repeat:
    calculate predictions
    calculate loss
    calculate gradient
    update parameters
Return learned parameters

The exact pseudocode changes by algorithm, but this separation matters:

algorithm idea
     ≠
Python syntax
20

Manual Trace Before Full Dataset

Suppose an algorithm operates on:

A → B
A → C
B → D
C → E

First trace:

start = A

by hand.

Only after the trace is understood should a larger graph be used.

Likewise for ML:

X = tiny matrix
y = tiny target

before using a large real dataset.

21

Complexity Is Part of Coding

An implementation is not complete until you understand its computational behaviour.

For algorithms, record:

\[ \boxed{\text{Time complexity}} \]

and

\[ \boxed{\text{Space complexity}} \]

where applicable.

For ML, also consider:

number of samples
number of features
number of parameters
epochs
batch size
memory

The same algorithm can behave very differently at different scales.

22

From-Scratch vs Production Code

A university implementation might prioritize:

clarity
↓
traceability
↓
correctness

Production software additionally demands:

clarity
correctness
testing
performance
maintainability
security
observability
reproducibility

The Coding Book should teach the bridge between the two.

Resource Rule

The supplied learning system says:

Syllabus
  ↓
Course notes
  ↓
Core video
  ↓
Practice / Python

The Coding Book therefore does not need to become a resource catalog.

Use one strong implementation route, then add a reference only when the implementation becomes unclear.

The resource guide identifies videos as the primary learning mode and Python as part of the practice layer.

27

Coding Progress States

Use:

C0 — Seen

I have read it.

C1 — Run

I have executed it.

C2 — Trace

I understand the state changes.

C3 — Rebuild

I can implement the core logic with reference to pseudocode.

C4 — Test

I can write tests.

C5 — Modify

I can change the implementation safely.

C6 — Explain

I can explain design, complexity, failure cases, and output.

C7 — Transfer

I can adapt the technique to a new problem.

Never mark a chapter “mastered” merely because the notebook executes.

Foundation Exit Test

⚠️ University Lab Viva Trap & Runtime Gotcha
**Hardcoded Dimensions & Global State Trap:** Never hardcode shapes (like `for i in range(100):`) or rely on global variables in lab practicals! Always use `X.shape[0]`, pass parameters cleanly to functions/classes, write assertion tests, and set random seeds (`np.random.seed(42)`) for 100% reproducible lab evaluations.

Before moving to CODE-01, answer:

  1. Why should pseudocode come before implementation?
  2. What does “from scratch” mean in this book?
  3. Why are library implementations placed after core implementations?
  4. What is the difference between a code error and an evaluation error?
  5. Why is shape checking important?
  6. What belongs in a reproducible experiment?
  7. Why should the test set be protected?
  8. Why should small hand-checkable examples come first?
  9. What are C0–C7?
  10. What makes a coding chapter complete?

Target

You should be able to explain the answers in your own words.
